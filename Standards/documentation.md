# Documentation Standard

[Standards index](README.md)

## Principle

Documentation is successful when another person can reproduce intent and behavior without asking the author to fill hidden gaps.

## Code documentation

Document:

- public interfaces/contracts;
- units;
- protocol fields;
- state meanings;
- nonobvious algorithms;
- hardware assumptions;
- failure behavior.

Do not narrate syntax line by line.

## Diagrams

Use a diagram when relationships are clearer visually:

- state machine;
- protocol frame;
- module/component boundary;
- data flow;
- sequence;
- flowchart.

A diagram must agree with the code/specification.

## README requirements for substantial work

State:

- problem/purpose;
- toolchain;
- build/run;
- configuration;
- test/verification;
- hardware/simulation;
- known limitations.

## Evidence documentation

Label:

- expected;
- actual;
- environment/version;
- test condition;
- result.

A screenshot should be used only when visual output itself is evidence.

## Durable wording

Avoid semester/week identifiers in durable topic/assignment identity unless the artifact is genuinely semester-specific.

Use section links for conceptual sequence and the LMS/calendar for dates.
